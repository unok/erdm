# ELK グラフ構築は Go（CLI）とフロント（SPA）で二重に持ち、契約テストで縛る

**Status:** accepted

ELK 入力グラフの構築は Go 側 `internal/elk`（CLI `--format=elk` の静的 JSON 出力）と
フロント側 `frontend/src/layout/elk.ts`（ブラウザで elkjs を実行してレイアウト計算）に
存在する。これらを単一実装へ統合するのではなく、**役割の異なる 2 実装として意図的に維持し、
一致すべき構造（グループ所属・エッジ集合）をクロスチェックテストで縛る**方針を採る。

## なぜ統合しないか

- **レイアウト計算は物理的にブラウザ側でしか走らない。** elkjs は JS 実装であり、
  Go からは実行できない。Go `internal/elk` は入力グラフを出力するだけで、
  レイアウトアルゴリズムを持たない。
- **ノードサイズは描画内容依存になる。** カラム表示（issue #28）を入れると、
  ノードの幅・高さは DOM 実測が必要で、本質的にブラウザ側の責務になる。
- したがって「Go を単一ソースにし SPA は API 経由で消費する」案は、サーバ往復を強制し、
  オフライン下書き再描画を壊し、かつサイズは結局ブラウザで上書きするため筋が悪い。
- `--format=elk` は README 掲載の公開機能（外部ツール向け）であり、削除も破壊的。

## 却下した代替案

- **A: Go を単一ソース化（`GET /api/elk`）** — サーバ往復・オフライン喪失・
  サイズのブラウザ上書きが残るため却下。
- **D: 片方を削除** — 公開機能 `--format=elk` の破壊、または SPA のフロント完結性の喪失。
- **WASM で Go コアを共有** — ELK に限れば elkjs もサイズ問題も残り過剰（issue #35 で
  serializer を第一ターゲットに別途 PoC）。

## 帰結

- フロント `elk.ts` に primary グループの階層（groupNode）を追加する（issue #27 の一部）。
- Go `internal/elk` とフロント `elk.ts` が**一致すべき構造**（ノードの
  グループ所属・sanitize 済みエッジ集合）について、シリアライザ同様のクロスチェック
  テストを追加し drift を検出する。座標・サイズ・layoutOptions は正当に異なるため
  完全一致ではなく「構造サブセット一致」で縛る。
